# 선택 안내: 작업 지도·설계·인계·독립 검토

AGENTS.md 의 기본 기준만으로 부족할 때 해당 절만 읽는다. 매 작업에 쓰지 않는다.

## 작업 지도: 결정·의존·완료 조건을 대화만으로 놓칠 위험이 있을 때

크기가 아니라 놓칠 가능성으로 고른다. 예: 정책이 충돌하거나 여러 요구가 얽힌 일, 여러 턴·세션에 걸친 일, 남에게 넘길 일.

- 위치는 `work/<작업명>/work.md`. 승인을 묻기 전에 쓴다. 승인은 그 지도의 `## 기준` 절에 묶이고, 그 절이 그대로인 동안 다음 메시지에도 유지된다. 끝나면 재사용할 결정을 반영하고 지도를 정리한다(승인이 닫힌다).
- `## 기준`에는 필요한 만큼만: 요청 원문 → 사용자가 볼 결과(입력 → 관찰 장소 → 기대) → 변경 뒤에도 지켜야 할 기존 보장과 그 연결 근거 → 확인 방법(조건을 어긴 경우를 검사가 실패로 잡는지 포함). 미정은 질문과 추천으로 따로 둔다.
- 설계(변경 위치·이유, 책임 나누기)와 실행 결과는 `## 기준` 밖에 둔다. 그래야 구현 방법이나 증거를 고쳐도 다시 묻지 않는다. 승인 뒤 `## 기준`을 고치는 것은 기준 변경이므로 다시 승인받는다.
- 인계할 때는 대상 버전·증거·남은 일·작성권을 지도에 갱신해 넘기고 받았는지 확인한다.

## 질문: 사용자 몫의 미정이 남았을 때

미정을 셋으로 나눈다. 원문·사용자 결정으로 이미 정해진 것(다시 묻지 않는다), 조사·실행으로 정할 수 있는 것(직접 정하고 근거를 적는다), 사용자 몫(결과·범위·권한·완료 기준이 갈림). 사용자 몫만 근거·추천 이유·선택에 따른 결과 차이와 함께 묻는다. 앞 답에 따라 달라지는 결정은 답을 받은 뒤 묻는다.

## 독립 검토: 직접 확인만으로 확인하기 어려운 공백이 있을 때

고르는 이유를 한 줄로 밝힌다: 어떤 보장이 깨질 수 있고, 직접 검사만으로 무엇을 확인하기 어려운가. 사용자가 요구하거나 검사를 지우·건너뛰·약화하는 기준 변경은 반드시 검토받는다. 지도가 없어도 된다.

1. `python3 .agents/skills/wf-verify/verify.py prepare` (지도가 있으면 `--map work/<작업명>/work.md`). 관문이 승인 때 고정한 요청 원문·승인받은 계획(지도면 그 기준)·승인 뒤 메시지와, 승인 뒤 변경(diff)·판정 대상 고정 복사본을 묶어 `prompt_file` 을 낸다. 원문이나 계획을 확보하지 못하면 입력 부족(미확인)으로 끝난다. 이때 요약한 계획으로 대신하지 않는다.
2. `prompt_file` 내용을 그대로 하네스의 하위 에이전트(검토자)에게 맡긴다. 검토자는 대상 폴더에서만 읽고 검사를 돌린다.
3. 검토자의 마지막 답을 고치지 않고 `verify.py finish --round <kept>` 의 표준 입력으로 넘긴다. ok 만 검토 통과다.
4. returned 면 사유를 원문·승인된 계획과 대조해 원인 자리로 돌아간다: 요구가 빠졌으면 요구 정의(사용자 몫이면 질문), 설계가 틀렸으면 설계, 구현이면 코드, 틀린 결과가 통과했으면 검사. 고친 뒤 prepare 부터 다시. incomplete(재검토 한도)는 미완료, unverified 는 사유·재개 조건과 함께 보고한다.

검토자 기준: 판정 범위는 바꾼 동작과 연결 근거가 있는 기존 보장이다. 요구의 근거는 사용자 원문과 외부 계약뿐이고 구현자의 자기평가는 근거가 아니다. 새 요구가 있어야 성립하는 반례는 범위 밖 제안으로 따로 적는다. 판정 중에는 아무것도 고치지 않는다.
