# 0007. 폼·상세·대화창·진행

- 출처: 2026-10-23 Q7·Q9·Q10·U3·U4와 구현 판정, 2026-10-28 폼·복잡한 폼·진행 표시 사용자 결정과 독립 판정, 2026-10-29 참조·두 번째 저장 승인. 결정권자: 사용자. 구현 선택은 아래 이유와 구분한다.
- 상태: 결정 통합(2026-10-30). 사용 보장 정본은 [web-kit-form](../../packages/web-kit/skills/web-kit-form/SKILL.md)·[web-kit-record](../../packages/web-kit/skills/web-kit-record/SKILL.md), 진행 조회는 [web-kit-list](../../packages/web-kit/skills/web-kit-list/SKILL.md)다. 사용자 원문의 프로젝트 사례는 결정 범위를 보존하는 일반 표현으로 바꿨다.

## 저장 수명과 상세

- 확인창 유무와 관계없이 저장 경로는 하나로 두고 확인한 값과 저장 값이 같게 한다. 성공 결과가 있으면 그 값을 기준선, 없으면 제출 값을 기준선으로 삼는다. 저장 중 편집이 없으면 입력에도 결과를 반영하고 편집이 있으면 입력을 보존한다. 폼 전체를 비교하고 필드별 병합은 하지 않는다(Q7·Q9·U3).
- 원본 재도착 때 손대지 않은 폼만 교체하고 고친 입력·저장 중 입력은 지킨다. 서버 정규화로 그대로 제출한 폼이 계속 수정됨으로 남던 문제를 막는다. 제출 값 복사는 File을 망가뜨리므로 하지 않고 기준선은 읽기 전용으로 낸다. blur 오류가 있어도 제출 전 전체 검증은 한다(구현 판정).
- `saved`·`acknowledge`·`complete()`는 저장 성공 뒤 이동 실패가 다시 저장 요청으로 이어지지 않게 한다. 완료 확인 여부는 화면 값이며 완료 재시도는 완료 처리만 한다. 저장 결과를 onSaved에 전달하여 새 ID 이동에 우회가 필요 없게 한다.
- 상세 상태는 화면 안 한 곳에서 판정하고 loader는 미리 받기만 한다. not-found와 현재 레코드 forbidden은 이전 내용을 숨기되 다른 요청의 forbidden까지 확대하지 않는다. 일시 갱신 실패는 내용을 유지하고 알린다(Q10·U4).
- 레코드 식별을 따로 받아 언어 전환 같은 재조회와 레코드 교체를 구분한다. `missing.wasReady`는 사실만 주고 표시 위치는 프로젝트가 정한다. Record 부품은 context로 조립하고 이력 날짜 포맷은 프로젝트가 작성한다.

## 폼 연결과 오류

- context 부품은 칸·버튼·오류 줄을 옮길 때 배선을 다시 쓰지 않게 한다. 한 줄 오류 판정은 `formFailure`, 문구·그리지 않음은 프로젝트가 맡는다. 실패한 선택지를 빈 select로 숨기지 않고 status·onRetry와 그 자리 실패·재시도 뒤 포커스를 연결한다.
- 빈 선택 항목을 값이 빌 때만 두는 선택은 잘못 비워 저장 실패를 만드는 길을 줄이려는 폼 설계 이유다. 별도 공용 채택 제안의 미정 상태는 아래에 보존한다.
- maxLength는 길어지는 편집만 제한하여 한글 조합 커밋을 자르는 네이티브 제한 문제를 피한다. FormGuard·useLeave는 공통 이탈 판정을 유지하며 취소·이동 문구 차이와 Router 밖 이탈은 입력·연결로 받는다.
- 저장 버튼은 `aria-disabled`로 잠가 확인창 종료 뒤 돌아올 포커스를 보존한다. 대화창은 열린 커밋의 첫 포커스와 Tab 경계를 동기 처리한다. Base UI focus guard의 다음 프레임 복귀에만 맡기면 그 사이 배경 요소를 읽을 수 있기 때문이다. 검사에서 기다려 결함을 숨기는 대안은 택하지 않는다.
- Form.Dialog와 제출 전파 차단으로 하위 폼을 격리한다. 닫기 때 묻지 않는 대화창은 protect=false를 사용한다. 폼·상세·대화창은 목록·권한·유휴 타이머를 import하지 않는다. 표현 부품은 registry에 두어 폼 밖 확인창이 폼 UI 입구를 끌어오지 않게 한다.
- 줄 작업은 키트 작업 기록으로 정체성을 추적한다. 중첩 배열의 첫 번호만 바꾸거나 값 안 key로 추측하면 다른 줄에 오류가 붙는다. 값 반영 후 해당 배열의 번호 오류를 옮기고 삭제된 줄 오류는 폼 한 줄로 낸다. 저장 중 구조 변경을 막는 대안은 편집 보존을 줄이므로 택하지 않는다.
- 요청 배열 번호를 폼 번호로 바꾸는 새 입력은 넣지 않았다. 당시 저장 시 요청과 폼 배열이 같았기 때문이다. 요청이 줄을 빼는 실제 요구가 확인되면 검토한다.
- 파일은 비어 있음·기존·새 파일·제거 네 상태로 보존하고 선택 창 취소는 값을 유지한다. 네이티브 입력 재생성으로 파일 이름을 잃지 않게 상태에서 표시한다. 업로드는 save에 조합하며 즉시 업로드는 저장 전 이탈 때 고아 파일을 남긴다.
- 필수 표시는 schema 하나로 판정한다. 칸마다 required를 따로 유지하거나 schema 내부 구조를 읽으면 조건부 규칙과 갈라진다. 고칠 수 없는 disabled 칸 오류는 숨기기만 하지 않고 붙지 못한 오류로 세어 폼 한 줄로 안내한다.
- 기본 여백 초기화는 `:where(...)`로 낮은 우선순위에 둔다. 클래스 우선순위 margin 초기화가 프로젝트 간격 유틸리티를 지우지 않게 한다(구현 선택).

## Enter 사용자 결정과 해석 정정

사용자 원문(2026-10-28): “폼에서 Enter는 기본적으로 제출(submit 클릭)이다. 단, [추가] 버튼이 딸린 입력칸(form-field-array, 검색어 칩 등)에서는 Enter가 제출 대신 [추가] 클릭으로 동작한다. 모달 안 입력칸의 Enter는 그 모달의 확인(모달 폼 제출)이며 바깥 폼은 제출되지 않는다.”

해석 정정(2026-10-28, 사용자 확정, 7단계 독립 검증 R6): “[추가] 버튼이 딸린 입력칸”은 **입력한 값을 목록에 넣는 칸**이다. 빈 줄만 더하는 배열 줄 입력은 일반 칸이므로 Enter=페이지 폼 제출이다. 모달 안 Enter는 모달 확인이며 바깥 폼은 제출도 검증도 하지 않는다. 새 옵션 대신 기존 enterAdds·Form.Dialog로 지킨다. 목록 검색어의 최신 키 연결 책임은 [목록·선택 결정](0006-list-choice-permission.md#선택-칸과-검색어)의 2026-10-30 결정이 정한다.

## 구역과 화면 절차 거절 사용자 결정

- 사용자 결정(2026-10-28): 구역 열고 닫기는 거절된 제출마다(클라이언트 검증 실패·서버 필드 오류 도착) 오류 구역을 모두 펼치고 첫 오류로 가는 사건 방식이다. 그 밖에는 사용자 열림 상태를 유지하고 제출 횟수를 기록하지 않는다. 기본 머리글은 “!”, 화면 낭독기는 messages.sectionErrors로 오류 수를 읽는다. 제출 횟수 비교는 저장 중 닫은 구역에 늦게 온 서버 오류를 펼치지 못해 폐기했다.
- 사용자 결정(2026-10-28): 머리글 표시는 프로젝트 선택이다. `errorMarker(errorCount)`로 “오류 2개” 같은 다른 표시를 줄 수 있다. 상태·처리 순서는 키트, 무엇을 보일지는 프로젝트가 맡는다. 구역이 자기 칸 fields를 알아야 접힌 오류를 펼칠 수 있다.
- 사용자 결정(2026-10-28): `reject(outcome)` 한 길을 키트로 모은다. save가 `FormRejection(칸·문구 목록, root?)`을 던지면 서버 필드 오류와 같은 길(칸 부착→구역·reveal 펼침→지난 포커스 취소→화면 순서 첫 오류)로 처리한다. 프로젝트는 거절 이유와 문구만 정한다. 복제 입구 revealFormSections는 공개에서 뺐고 프로젝트 고유 접힘도 reveal 사건으로 연다.

## 진행 덮개 사용자 결정

- 사용자 요청(2026-10-28): “저장 하거나 수정할 때 전체 등록중입니다... 혹은 수정중입니다... 이런 전체 모달이 나오면서 input을 막는식으로.” 폼이 create·edit 종류를 선언한다. mutation 개수로 덮으면 삭제·상태 변경도 등록 중으로 보이므로 저장 절차 전체의 진행을 따른다.
- step.waitForUser 동안 덮개를 내리고 확인창→덮개→완료 창 순서를 지킨다. 페이지 첫 조회는 progress='page'로 역할을 선언한다. 같은 query도 화면마다 진입 대기·하위 칸 역할이 달라 query meta만으로 정하지 않는다.
- 본문 inert·aria-busy와 늘 있는 status 영역을 쓰고 덮개를 대화창 형제로 두어 포커스를 다투지 않게 한다. 닫힐 때 본문 밖으로 밀린 경우만 마지막 본문 포커스로 복귀한다. 사라졌으면 제목→본문을 대체 자리로 쓰고 완료 창·오류 칸 포커스나 첫 진입은 건드리지 않는다.
- 사용자 결정(2026-10-28, 작업 7b Q1 “다”): **“목록 일괄 삭제·상세 삭제는 덮개 ‘삭제 중입니다. 잠시만 기다려 주세요.’, 상태 변경·대화창 폼 저장은 지금처럼 버튼 잠금 + 옆 진행 표시.”** 확인창을 거친 삭제는 useConfirmationState의 progress='delete'로 선언한다. selection.run에는 당시 삭제 소비자가 없어 선언하지 않았다.
- 사용자 결정(2026-10-28, 7b 후속): 가운데 진행 표시는 프로젝트 선택이며 기본 원형 표시는 indicator로 바꿀 수 있다. 모양·문구·표시층은 프로젝트 디자인 소유다. 특정 화면 디자인을 키트의 제품 기준으로 삼지 않는다.
- 지연·최소 표시는 두지 않는다. 지연은 짧은 저장 중 입력을 열고 최소 표시는 끝난 뒤에도 막기 때문이다. 덮개 미선언 쓰기는 버튼 잠금·옆 표시를 유지하며 Pending 부품을 공유한다. 앱 셸에 BlockingProgress가 연결됐는지는 실제 화면으로 검사한다.

## 참조와 두 번째 저장

2026-10-28 폼 합의 5-4·5-6과 2026-10-29 사용자 추가 승인이다. 원본 ID 목록·참조 필드 경로는 프로젝트 입력이며 삭제·해제·값 교체는 관계마다 함께 정리(기본, 사용 칸 수 확인) / 막기 / 저장 시 오류를 고른다. 확인 중 입력·원본·레코드·수명이 바뀌면 옛 변경을 적용하지 않고 줄 오류 이동을 보존한다. 업무 이름·값을 키트가 알지 않는다.

두 번째 저장은 자체 schema·save·완료 처리를 쓰되 같은 제출 잠금·기준선·실패·이탈 보호를 공유한다. 성공 직후 이탈은 묻지 않고 이후 수정은 다시 묻는다. 두 저장을 별도 상태로 구현하면 동시 제출·기준선 불일치가 생기므로 기존 실행·완료 경로를 사용한다.

## 미정과 결정 안 됨

- 숨긴 조건부 칸을 검증·제출에서 빼고 다시 보이면 값을 되살리는 것은 작성자 추천이며 사용자 결정 전이다.
- 업로드 흐름의 단계별 상태·취소·재시도 규칙은 미정이다. 화면 관찰을 공용 설계 승인으로 보지 않는다.
- 빈 값일 때만 Select의 빈 항목을 보이는 공용 채택 제안(당시 폼 5-10)은 사용자 결정이 아니다. 앞의 기존 폼 구현 선택과 이 제안의 승인 상태를 섞지 않는다.
