# 0007. 폼·상세·대화창·진행

- 출처: 2026-10-23 폼·상세 사용자 결정과 구현 판정, 2026-10-28 폼·복잡한 폼·진행 표시 사용자 결정과 독립 판정, 2026-10-29 참조·두 번째 저장 승인. 결정권자: 사용자. 구현 선택은 아래 이유와 구분한다.
- 상태: 결정 통합(2026-10-30). 사용 보장 정본은 [web-kit-form](../../packages/web-kit/skills/web-kit-form/SKILL.md)·[web-kit-record](../../packages/web-kit/skills/web-kit-record/SKILL.md), 진행 조회는 [web-kit-list](../../packages/web-kit/skills/web-kit-list/SKILL.md)다. 사용자 원문의 프로젝트 사례는 결정 범위를 보존하는 일반 표현으로 바꿨다.

## 저장 수명과 상세

- 확인창 유무와 관계없이 저장 경로는 하나로 두고 확인한 값과 저장 값이 같게 한다(2026-10-23 사용자 결정). 저장 후 입력과 기준선이 어긋나거나 진행 중 편집을 잃지 않게 하기 위한 선택이다. 기준선 갱신과 편집 보존 조건은 [폼 스킬의 저장·완료·이탈](../../packages/web-kit/skills/web-kit-form/SKILL.md#키트-보장)이 정본이다.
- 원본 재도착과 서버 정규화로 고친 입력을 잃거나 그대로 제출한 폼이 계속 수정됨으로 남던 문제를 막는다(2026-10-23 구현 판정). 원본·File·검증의 처리 조건은 같은 폼 스킬을 따른다.
- `saved`·`acknowledge`·`complete()`는 저장 성공 뒤 이동 실패가 다시 저장 요청으로 이어지지 않게 한다. 완료 확인 여부는 화면 값이며 완료 재시도는 완료 처리만 한다. 저장 결과를 onSaved에 전달하여 새 ID 이동에 우회가 필요 없게 한다.
- 상세 상태는 화면 안 한 곳에서 판정하고 loader는 미리 받기만 한다. not-found와 현재 레코드 forbidden은 이전 내용을 숨기되 다른 요청의 forbidden까지 확대하지 않는다. 일시 갱신 실패는 내용을 유지하고 알린다(2026-10-23 사용자 결정).
- 레코드 식별을 따로 받아 언어 전환 같은 재조회와 레코드 교체를 구분한다. `missing.wasReady`는 사실만 주고 표시 위치는 프로젝트가 정한다. Record 부품은 context로 조립하고 이력 날짜 포맷은 프로젝트가 작성한다.

## 폼 연결과 오류

- context 부품은 칸·버튼·오류 줄을 옮길 때 배선을 다시 쓰지 않게 한다. 한 줄 오류 판정은 `formFailure`, 문구·그리지 않음은 프로젝트가 맡는다. 실패한 선택지를 빈 select로 숨기지 않고 status·onRetry와 그 자리 실패·재시도 뒤 포커스를 연결한다.
- 빈 선택 항목을 값이 빌 때만 두는 선택은 잘못 비워 저장 실패를 만드는 길을 줄이려는 폼 설계 이유다. 별도 공용 채택 제안의 미정 상태는 아래에 보존한다.
- maxLength는 길어지는 편집만 제한하여 한글 조합 커밋을 자르는 네이티브 제한 문제를 피한다. FormGuard·useLeave는 공통 이탈 판정을 유지하며 취소·이동 문구 차이와 Router 밖 이탈은 입력·연결로 받는다.
- 저장 버튼은 `aria-disabled`로 잠가 확인창 종료 뒤 돌아올 포커스를 보존한다. 대화창은 열린 커밋의 첫 포커스와 Tab 경계를 동기 처리한다. Base UI focus guard의 다음 프레임 복귀에만 맡기면 그 사이 배경 요소를 읽을 수 있기 때문이다. 검사에서 기다려 결함을 숨기는 대안은 택하지 않는다.
- Form.Dialog와 제출 전파 차단으로 하위 폼을 격리한다. 닫기 때 묻지 않는 대화창은 protect=false를 사용한다. 폼·상세·대화창은 목록·권한·유휴 타이머를 import하지 않는다. 표현 부품은 registry에 두어 폼 밖 확인창이 폼 UI 입구를 끌어오지 않게 한다.
- 줄 작업은 키트 작업 기록으로 정체성을 추적한다. 중첩 배열의 첫 번호만 바꾸거나 값 안 key로 추측하면 다른 줄에 오류가 붙기 때문이다. 저장 중 구조 변경을 막는 대안은 편집 보존을 줄이므로 택하지 않는다. 오류 이동 절차는 [폼 스킬](../../packages/web-kit/skills/web-kit-form/SKILL.md)이 정본이다.
- 요청 배열 번호를 폼 번호로 바꾸는 새 입력은 넣지 않았다. 당시 저장 시 요청과 폼 배열이 같았기 때문이다. 요청이 줄을 빼는 실제 요구가 확인되면 검토한다.
- 파일은 비어 있음·기존·새 파일·제거 네 상태로 보존하고 선택 창 취소는 값을 유지한다. 네이티브 입력 재생성으로 파일 이름을 잃지 않게 상태에서 표시한다. 업로드는 save에 조합하며 즉시 업로드는 저장 전 이탈 때 고아 파일을 남긴다.
- 필수 표시는 schema 하나로 판정한다. 칸마다 required를 따로 유지하거나 schema 내부 구조를 읽으면 조건부 규칙과 갈라진다. 고칠 수 없는 disabled 칸 오류는 숨기기만 하지 않고 붙지 못한 오류로 세어 폼 한 줄로 안내한다.
- 기본 여백 초기화는 `:where(...)`로 낮은 우선순위에 둔다. 클래스 우선순위 margin 초기화가 프로젝트 간격 유틸리티를 지우지 않게 한다(구현 선택).

## Enter 사용자 결정과 해석 정정

사용자 원문(2026-10-28): “폼에서 Enter는 기본적으로 제출(submit 클릭)이다. 단, [추가] 버튼이 딸린 입력칸(form-field-array, 검색어 칩 등)에서는 Enter가 제출 대신 [추가] 클릭으로 동작한다. 모달 안 입력칸의 Enter는 그 모달의 확인(모달 폼 제출)이며 바깥 폼은 제출되지 않는다.”

해석 정정(2026-10-28, 사용자 확정): “[추가] 버튼이 딸린 입력칸”은 **입력한 값을 목록에 넣는 칸**이다. 빈 줄만 더하는 배열 줄 입력은 일반 칸이므로 Enter=페이지 폼 제출이다. 모달 안 Enter는 모달 확인이며 바깥 폼은 제출도 검증도 하지 않는다. 새 옵션 대신 기존 enterAdds·Form.Dialog로 지킨다. 목록 검색어의 최신 키 연결 책임은 [목록·선택 결정](0006-list-choice-permission.md#선택-칸과-검색어)의 2026-10-30 결정이 정한다.

## 구역과 화면 절차 거절 사용자 결정

- 사용자 결정(2026-10-28): 구역 열고 닫기는 거절된 제출마다(클라이언트 검증 실패·서버 필드 오류 도착) 오류 구역을 모두 펼치고 첫 오류로 가는 사건 방식이다. 그 밖에는 사용자 열림 상태를 유지하고 제출 횟수를 기록하지 않는다. 기본 머리글은 “!”, 화면 낭독기는 messages.sectionErrors로 오류 수를 읽는다. 제출 횟수 비교는 저장 중 닫은 구역에 늦게 온 서버 오류를 펼치지 못해 폐기했다.
- 사용자 결정(2026-10-28): 머리글 표시는 프로젝트 선택이다. `errorMarker(errorCount)`로 “오류 2개” 같은 다른 표시를 줄 수 있다. 상태·처리 순서는 키트, 무엇을 보일지는 프로젝트가 맡는다. 구역이 자기 칸 fields를 알아야 접힌 오류를 펼칠 수 있다.
- 사용자 결정(2026-10-28): `reject(outcome)` 한 길을 키트로 모은다. save가 `FormRejection(칸·문구 목록, root?)`을 던지면 서버 필드 오류와 같은 길(칸 부착→구역·reveal 펼침→지난 포커스 취소→화면 순서 첫 오류)로 처리한다. 프로젝트는 거절 이유와 문구만 정한다. 복제 입구 revealFormSections는 공개에서 뺐고 프로젝트 고유 접힘도 reveal 사건으로 연다.

## 진행 덮개 사용자 결정

- 사용자 요청(2026-10-28): “저장 하거나 수정할 때 전체 등록중입니다... 혹은 수정중입니다... 이런 전체 모달이 나오면서 input을 막는식으로.” 폼이 create·edit 종류를 선언한다. mutation 개수로 덮으면 삭제·상태 변경도 등록 중으로 보이므로 저장 절차 전체의 진행을 따른다.
- 진행은 요청 개수 대신 화면이 선언한 역할을 따른다. 같은 query도 진입 대기·하위 칸 역할이 다르기 때문이다. 확인창·덮개·완료 창 순서와 조회 연결은 [폼 스킬의 진행 덮개](../../packages/web-kit/skills/web-kit-form/SKILL.md#화면-전체-진행-덮개)가 정본이다.
- 덮개를 대화창과 분리하고 종료 뒤 읽을 위치를 보존한다. 배경 포커스 유실과 대화창의 포커스 경쟁을 막기 위한 선택이다. 본문 차단·상태 알림·포커스 복귀 조건은 같은 진행 덮개 절을 따른다.
- 사용자 결정(2026-10-28): **“목록 일괄 삭제·상세 삭제는 덮개 ‘삭제 중입니다. 잠시만 기다려 주세요.’, 상태 변경·대화창 폼 저장은 지금처럼 버튼 잠금 + 옆 진행 표시.”** 확인창을 거친 삭제는 useConfirmationState의 progress='delete'로 선언한다. selection.run에는 당시 삭제 소비자가 없어 선언하지 않았다.
- 사용자 결정(2026-10-28): 가운데 진행 표시는 프로젝트 선택이며 기본 원형 표시는 indicator로 바꿀 수 있다. 모양·문구·표시층은 프로젝트 디자인 소유다. 특정 화면 디자인을 키트의 제품 기준으로 삼지 않는다.
- 지연·최소 표시는 두지 않는다. 지연은 짧은 저장 중 입력을 열고 최소 표시는 끝난 뒤에도 막기 때문이다. 연결·검사는 같은 진행 덮개 절을 따른다.

## 참조와 두 번째 저장

2026-10-28 폼 사용자 결정과 2026-10-29 사용자 추가 승인이다. 업무 이름·값과 관계 정책은 프로젝트 입력이며 참조 확인·값 적용은 공용 흐름으로 채택했다. 수명 변화 중 옛 확인 결과 적용을 막기 위해서다. 관계 선언과 처리 조건은 [폼 스킬의 원본과 참조](../../packages/web-kit/skills/web-kit-form/SKILL.md#폼-안-원본과-참조)가 정본이다.

두 번째 저장도 기존 실행·완료 경로를 사용한다. 별도 상태로 구현하면 동시 제출·기준선 불일치가 생기기 때문이다. 입력과 보호 조건은 [폼 스킬의 두 번째 저장](../../packages/web-kit/skills/web-kit-form/SKILL.md#같은-폼의-두-번째-저장)이 정본이다.

## 조건부 칸 사용자 결정

사용자 결정(2026-10-30): 조건 때문에 숨긴 칸은 다시 보이면 원래 값(등록 기본값·불러온 값·저장 성공 뒤 저장된 값)으로 돌아가고, 숨긴 채 저장하면 프로젝트가 정한 빈 값을 보내며 숨긴 동안 필수 검증으로 저장을 막지 않는다. 키트는 수명 처리를, 프로젝트는 숨기는 조건과 서버 빈 값의 모양을 소유한다. 다른 분석 문서의 “숨긴 동안 편집값 보관 후 복원” 안은 채택하지 않았다.

추가 해석(2026-10-30 조정자 판정): 조건부 필수는 schema가 같은 조건 함수로 표현한다. Standard Schema는 실패 시 변환 출력을 주지 않으므로 키트가 숨긴 오류를 지우고 입력을 출력으로 간주하는 안은 채택하지 않았다. 빈 값을 거절하는 schema 연결 오류는 폼 한 줄로 드러낸다. 새 줄은 등록과 같아 append 최초 값이 원래 값이다. 보장·선언 정본은 [폼 스킬의 조건부 칸](../../packages/web-kit/skills/web-kit-form/SKILL.md#조건부로-숨기는-칸)을 따른다.

## 미정과 결정 안 됨

- 업로드 흐름의 단계별 상태·취소·재시도 규칙은 미정이다. 화면 관찰을 공용 설계 승인으로 보지 않는다.
- 빈 값일 때만 Select의 빈 항목을 보이는 공용 채택 제안은 사용자 결정이 아니다. 앞의 기존 폼 구현 선택과 이 제안의 승인 상태를 섞지 않는다.
