## 범위와 역할

- 프로젝트가 필요한 공용 기능을 선택해 조립한다. 사용하는 프로젝트 수나 화면의 닮은 정도보다 정상·실패·취소·늦은 응답까지 같은 책임인지 비교한다. 특정 업무의 성공 판정은 프로젝트 또는 별도 업무 패키지에 둔다.
- 키트는 공통 상태·수명·오류 처리, 프로젝트는 제품 요구·서버 계약·성공 의미·코드 의미·문구·번역·업무 처리·실제 화면을 소유한다. 서버마다 다른 사실을 키트 기본값으로 넣지 않는다.
- 기존 시나리오는 보존할 제품 결과의 근거다. 키트 채택 때문에 승인되지 않은 제품 동작을 바꾸지 않는다. 표현할 수 없는 차이는 공용 보장의 결함·공통 기능 부족·제품 차이로 먼저 구분한다.
- 편입 규칙(U5): 공통 보장을 완성하는 책임은 키트, 업무 의미 때문에 달라지는 흐름은 프로젝트가 조합한다. 내부 변경이 필요하다는 사실만으로 키트에 넣지 않는다.
- 구조는 화면 하나를 고칠 때 알아야 할 규칙을 줄여야 한다. 같은 판단을 두 곳에 두지 않고 옮긴 책임은 원래 자리에서 지운다. 현재 구현 자체를 제품 정책의 근거로 삼지 않는다.
- 화면은 제목·필터·작업·결과가 읽히는 일반 JSX 부품으로 조립한다. 업무 처리 콜백은 이름 있는 함수, 짧은 값 선택·전달은 인라인으로 두고 모델·업무 연결·UI·배치를 책임별로 나눈다. 파일 수는 강제하지 않는다. 조립과 채택한 장점의 유지 여부는 starter와 실제 설치 검사로 확인한다.

## 페이지 일부만 다른 경우

페이지 전체는 프로젝트가 조립한다. 같은 동작의 값 차이는 공개 입력, 업무 차이는 프로젝트 함수로 연결한다. 예를 들어 등록 폼 검증·중복 제출 방지는 키트, 필드·요청 변환·승인 API·완료 목적지·선택적 첨부 UI는 프로젝트가 맡는다.

- 모양은 UI 복사본에서 바꾸고 같은 상태를 프로젝트에서 다시 관리하지 않는다.
- 업무 차이 때문에 공통 저장 수명을 복제하거나 키트에 프로젝트 이름별 분기를 넣지 않는다.
- 공개 연결로 표현할 수 없으면 실제 요구와 범위를 검토한다. 공통 보장 결함은 키트, 별도 제품 책임은 프로젝트에 둔다.
- 상세 안 하위 목록·폼 배열·선택 팝업은 각자의 상태 수명에 맞춘다. 표 모양이 같다고 모두 URL 기반 목록으로 만들지 않는다.

## 구조와 저장소

- 순수 규칙은 외부 상태·실행 없이 입력만으로 결과를 정하며 루트로 공개한다. 라이브러리에 의존하지 않아도 세션처럼 실행·부수효과가 있으면 순수 규칙이 아니다. 필요한 라이브러리 연결은 책임별 입구로 둔다.
- 기능별 입구와 한 방향 의존을 유지한다. UI는 로직을 사용하고 로직은 프로젝트 UI를 import하지 않는다. 목록·폼은 서로 또는 세션 타이머·권한을 끌어오지 않는다. 선택한 기능 안 상태·처리 순서의 소유자는 하나다.
- `packages/web-kit`은 공통 동작·같은 버전의 사용 스킬·적합성 검사, `packages/ui-registry`는 복사할 UI와 검사 연결, `apps/starter`는 실행 시작점이자 실제 산출물 소비 검사다. 현재 입구는 [패키지 구조](../../packages/web-kit/README.md#구조)와 package.json exports로 찾는다.
- starter는 기본 연결·조립 예이며 제품의 표준 페이지가 아니다. 별도 starter 저장소나 기능 조합별 생성기는 만들지 않는다. 예시 필드·문구·권한은 제품 정책이 아니다. 사용하지 않은 기능까지 검증됐다고 하지 않는다.
- 발권(실시간 연결·프린터·발권 성공 판정)은 별도 업무 책임으로 필요할 때 `packages/ticketing`으로 분리한다. 지금 폴더를 만들지 않는다. 세션이 발권을 import하지 않고 발권이 종료를 구독한다. 다른 패키지 분리도 독립 소비자·의존성·배포 요구가 확인될 때 판단한다.
- agent-workflow-kit은 웹과 무관한 작업 판단·검증 방법을 맡는다. 버전 태그로 고정하고 web-kit 적용 PR에서 함께 올린다. 태그 없는 후보 검증에서는 깨끗한 checkout과 해소된 commit을 기록하고 정식 태그 도입 완료라고 하지 않는다.
- 같은 버전에는 한 내용만 둔다. 새 선택 기능과 기존 사용의 호환은 [버전 기준](../maintaining.md#버전-기준), UI 소유는 [배포 결정](0002-distribution.md)을 따른다. 이 원칙이 아직 없는 공개 교체 지점을 약속하지는 않는다.

## 검토한 대안

- 페이지 전체 템플릿 고정은 업무 분기를 쌓으므로 작은 기능을 조립한다.
- 로직만 제공하면 포커스·이벤트 연결 결함을 반복하므로 기본 UI와 검사 연결도 복사해 제공한다.
- 기능별 패키지를 먼저 나누면 독립 배포 요구 없이 호환 조합만 늘어나므로 기능별 입구로 선택한다.
- 공용 전체를 만든 뒤 한꺼번에 적용하면 연결 누락을 늦게 발견하므로 대표 흐름으로 확인하며 넓힌다.
