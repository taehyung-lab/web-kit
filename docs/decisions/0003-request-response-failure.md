# 0003. 요청·응답·실패

- 결정권자: 사용자. 출처: 2026-10-23 구조·수명 사용자 결정과 구현 판정, 2026-10-28 공용 경계 합의, 2026-10-30 응답 계약 필수 입력 사용자 승인.
- 상태: 결정 통합(2026-10-30). 아래 외부 계약은 여전히 미확인이다. 동작·입력의 정본은 [web-kit-http](../../packages/web-kit/skills/web-kit-http/SKILL.md)다.

## 응답 해석의 소유

서버 응답 형식·성공 판정·코드 의미는 프로젝트가 명시적으로 선택한다. Spring 해석은 이름 있는 선택 부품 `springEnvelope`로 두고 공통 요청 입구의 생성 봉투 타입 전제를 제거한다. 다른 형식의 정상 응답이 고정 봉투 해석 실패가 되던 원인을 기본값 자리에서 없앤다. 생략 허용이나 예외 플래그는 추가하지 않는다.

실패 형태·전송·회복은 키트가 맡고 의미·문구·번역은 프로젝트가 맡는다. 재발급 전용 코드 의미가 일반 요청과 다르면 프로젝트 `reissue` adapter가 `endsSession`·`messageKey`로 표현한다. 같으면 같은 실패를 전달한다.

## 전송과 회복의 선택 이유

- 쓰기는 자동 재시도하지 않는다. 조회의 재시도 대상은 network·timeout·server-error이며 횟수는 프로젝트 입력이다. 업무 중복 실행을 피하기 위한 선택이다.
- 반영 여부 미확정(`resultUnknown`)은 실패 종류만으로 정하지 않고 전송 경로를 아는 http가 판정한다. 하지 않은 업무까지 재확인 대상으로 만들지 않는다.
- 401 하나로 세션 종료를 정하지 않는다. 재전송을 끝내는 것과 세션을 끝내는 것은 다른 결정이므로 인증 계약으로 판정한다.
- 회전된 옛 토큰의 거절은 현재 토큰으로 다시 보낸다. 여러 탭·재발급 직후 옛 토큰 요청이 생길 수 있기 때문이다. 새 근거가 있을 때만 반복하며 쓰기는 E1 전제 없이는 다시 보내지 않는다.
- 쓰기 401 재전송 가능 여부는 키트 상수가 아니라 확인한 서버를 쓰는 프로젝트 입력으로 켤 책임이다. 실행 전 거절 여부는 서버마다 다른 사실이므로 한 서버의 확인으로 모든 소비자의 기본값을 바꾸지 않는다. 현재 입력 제공 여부는 공개 타입을 따른다.
- 전송 관찰은 `observe` 한 입구로 연결한다. 자기 응답의 마감이 필요한 연장에는 요청별 응답 메타를 제공하여 전역 최신 표본과 동시 요청을 섞지 않는다(2026-10-30 책임 분리 결정).
- 실패 판별은 전역 Symbol 표시를 쓴다. 한 앱에 패키지가 두 벌 로드되면 `instanceof`가 실패하기 때문이다. 실패 입력은 `messageKey`·`endsSession`, 종료·알림에는 출처 `by`를 전달하여 프로젝트 우회 코드를 줄인다(구현 선택).

## 반영 안 함

2026-10-23 구현 판정에서 다시 제안하지 않도록 남긴 목록이다.

- 문자열 resultCode: E2에서 실제 계약을 확인한다.
- resultMessage 문구 조회: 결과 코드 표의 메시지 키 행으로 대신한다.
- 요청별 응답 헤더: 당시에는 axios 표준 기능으로 조합한다고 제외했다. **2026-10-30 결정으로 이 항목만 갱신**하여 요청별 응답 메타를 전송 경로에서 제공한다. 자기 연장 응답을 전역 변수 없이 식별해야 하기 때문이다.
- 묶음 복구 값 지정: 기본값 하나를 유지한다.
- 빈 이전 페이지 구분: 추가하지 않는다.

## 미확인 외부 계약

서버마다 확인할 질문이다. 문서 통합으로 확인된 것이 아니며, 확인 전 해당 부분만 보류한다.

- **E1:** 그 401 응답이 업무 실행 전에 발생하는가. 확인 전에는 쓰기를 자동으로 다시 보내지 않는다.
- **E2:** 일반 요청과 재발급 요청 각각에서 status·resultCode가 재발급 시도, 최종 인증 실패, 세션 종료 중 무엇을 뜻하는가. HTTP 200 봉투의 종결 코드도 포함한다. resultCode가 문자열(`'200'`·`'SUCCESS'`)로 오는 경우가 있는가. 보류 대상은 결과 코드 표의 세션 종료 행이다.
- **E3:** 여러 탭이 동시에 재발급하면 어떻게 되는가. refresh 토큰을 회전하는지와 탭끼리 공유하는지, 이전 refresh 토큰을 다시 쓰면 어떻게 되는지, 회전 유예 시간, 먼저 발급한 access 토큰이 계속 유효한지를 확인한다. 로그아웃·계정 교체 뒤 이전 재발급 응답이 도착했을 때, 그 응답의 쿠키 변경이 새 세션에 영향을 줄 수 있는지도 확인한다(키트는 결과를 무시할 뿐 브라우저의 쿠키 변경은 막지 못한다). 보류 대상은 여러 탭 재발급을 조정하는 구체 방식과 서버·쿠키 격리 보장이다.
