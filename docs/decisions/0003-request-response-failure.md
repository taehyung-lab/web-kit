## 응답 해석의 소유

서버 응답 형식·성공 판정·코드 의미는 프로젝트가 명시적으로 선택한다. Spring 해석은 이름 있는 선택 부품 `springEnvelope`로 두고 공통 요청 입구의 생성 봉투 타입 전제를 제거한다. 다른 형식의 정상 응답이 고정 봉투 해석 실패가 되던 원인을 기본값 자리에서 없앤다. 생략 허용이나 예외 플래그는 추가하지 않는다.

실패 형태·전송·회복은 키트가 맡고 의미·문구·번역은 프로젝트가 맡는다. 재발급 전용 코드 의미가 일반 요청과 다르면 프로젝트 `reissue` adapter가 `endsSession`·`messageKey`로 표현한다. 같으면 같은 실패를 전달한다.

### 프로젝트 세부 코드 (2026-11-23 사용자 결정)

출처: 사용자 2026-11-23 "web-kit에서는 resultCode 공용으로 하고 각 프로젝트에서 data.code를 선언해서 사용", "세부 코드는 프로젝트마다 같은 코드여도 내용이 다를 수 있고 없는 코드일 수도 있다".

- 키트는 결과 코드로 종류·문구 키·세션 종료를 판정하고, 같은 결과 코드 안의 이유를 나누는 서버 값은 실패의 `detailCode`로 뜻 없이 운반만 한다. 위치는 프로젝트가 읽기 규칙으로 정한다.
- 이유: 소비 프로젝트가 세부 코드를 문구 키로 바꿔 `messageKey`를 덮어쓰자, 결과 코드의 뜻이 지워지고 화면이 문구 키 문자열을 비교해 실패를 되찾게 됐다. 같은 상황에 문구가 두 벌 생겼고 업무 코드 표가 공용 위치에 모였다. 실패의 정체(결과 코드·세부 코드)와 문구 선택을 분리해 원인 자리에서 없앤다.
- 고르지 않은 안: 세부 코드를 결과 코드 표의 세 번째 열로 두는 안. 세부 코드의 뜻은 업무마다 달라 키트 표가 가질 수 없고, 같은 값이 프로젝트마다 다르게 쓰인다.

## 전송과 회복의 선택 이유

- 쓰기는 자동 재시도하지 않는다(401 회복의 재전송은 아래 별도 결정). 조회의 재시도 대상은 network·timeout·server-error이며 횟수는 프로젝트 입력이다. 업무 중복 실행을 피하기 위한 선택이다.
- 반영 여부 미확정(`resultUnknown`)은 실패 종류만으로 정하지 않고 전송 경로를 아는 http가 판정한다. 하지 않은 업무까지 재확인 대상으로 만들지 않는다.
- 401 하나로 세션 종료를 정하지 않는다. 재전송을 끝내는 것과 세션을 끝내는 것은 다른 결정이므로 인증 계약으로 판정한다.
- 회전된 옛 토큰의 거절은 현재 토큰으로 다시 보낸다. 여러 탭·재발급 직후 옛 토큰 요청이 생길 수 있기 때문이다. 조회는 새 근거가 있을 때만 반복한다.
- 쓰기 401 재전송은 `createHttp`의 필수 입력 `authRejectsBeforeExecution`으로 프로젝트가 정한다(2026-11-25 결정). 401은 HTTP 의미상 "인증이 없어 적용되지 않은 요청"(RFC 9110 15.5.2)이라, 서버가 그 의미를 지키면 쓰기도 재발급 뒤 다시 보내는 것이 맞다. 이전에는 키트 안의 상수가 쓰기 재전송을 막아, 서버를 확인한 프로젝트도 토큰 만료 직후의 저장마다 "반영 여부 미확정"을 받았다. 실행 전 거절 여부는 서버마다 다른 사실이므로 키트 기본값을 두지 않고 필수 입력으로 받는다.
  - 켜도 쓰기는 HTTP 401일 때만 다시 보낸다. E1이 보증하는 것은 401뿐이고, HTTP 200 봉투의 종료 행은 업무 뒤에 나왔을 수 있다(독립 검토 반례).
  - 켜면 쓰기의 추가 전송은 옛 토큰 재전송과 재발급 재전송을 합쳐 한 번이다. 조회처럼 회전마다 반복하면 서버가 의미를 어긴 경우 같은 쓰기가 여러 번 반영될 수 있기 때문이다.
  - 재전송 직전에 로그인 세대를 확인해 옛 로그인의 요청을 새 로그인 토큰으로 보내지 않는다. 응답 뒤의 세대 확인만으로는 이미 나간 요청을 되돌리지 못한다.
  - 운영 헤더(`prepare`)는 요청 하나에 한 번 정하고 재전송은 그 값을 쓴다. 서버 기록이 원 조작의 맥락(화면·언어)을 가리키게 하기 위해서다.
  - 고르지 않은 안: 키트 기본값을 true로 바꾸는 안(확인하지 않은 서버에도 켜진다), 선택 입력으로 두고 기본 false인 안(숨은 기본값이 다시 생긴다).
- 전송 관찰은 `observe` 한 입구로 연결한다. 자기 응답의 마감이 필요한 연장에는 요청별 응답 메타를 제공하여 전역 최신 표본과 동시 요청을 섞지 않는다(2026-10-30 책임 분리 결정).
- 실패 판별은 전역 Symbol 표시를 쓴다. 한 앱에 패키지가 두 벌 로드되면 `instanceof`가 실패하기 때문이다. 실패 입력은 `messageKey`·`endsSession`, 종료·알림에는 출처 `by`를 전달하여 프로젝트 우회 코드를 줄인다(구현 선택).

## 반영 안 함

2026-10-23 구현 판정에서 다시 제안하지 않도록 남긴 목록이다.

- 문자열 resultCode: E2에서 실제 계약을 확인한다.
- resultMessage 문구 조회: 결과 코드 표의 메시지 키 행으로 대신한다.
- 요청별 응답 헤더: 당시에는 axios 표준 기능으로 조합한다고 제외했다. **2026-10-30 결정으로 이 항목만 갱신**하여 요청별 응답 메타를 전송 경로에서 제공한다. 자기 연장 응답을 전역 변수 없이 식별해야 하기 때문이다.
- 묶음 복구 값 지정: 기본값 하나를 유지한다.
- 빈 이전 페이지 구분: 추가하지 않는다.

## 미확인 외부 계약

서버마다 확인할 질문이다. 문서 통합으로 확인된 것이 아니며, 확인 전 해당 부분만 보류한다.

- **E1:** 그 401 응답이 업무 실행 전에 발생하는가. 프로젝트가 확인해 `authRejectsBeforeExecution`으로 넘긴다. 확인하지 못했으면 false로 두어 쓰기를 자동으로 다시 보내지 않는다.
- **E2:** 일반 요청과 재발급 요청 각각에서 status·resultCode가 재발급 시도, 최종 인증 실패, 세션 종료 중 무엇을 뜻하는가. HTTP 200 봉투의 종결 코드도 포함한다. resultCode가 문자열(`'200'`·`'SUCCESS'`)로 오는 경우가 있는가. 보류 대상은 결과 코드 표의 세션 종료 행이다.
- **E3:** 여러 탭이 동시에 재발급하면 어떻게 되는가. refresh 토큰을 회전하는지와 탭끼리 공유하는지, 이전 refresh 토큰을 다시 쓰면 어떻게 되는지, 회전 유예 시간, 먼저 발급한 access 토큰이 계속 유효한지를 확인한다. 로그아웃·계정 교체 뒤 이전 재발급 응답이 도착했을 때, 그 응답의 쿠키 변경이 새 세션에 영향을 줄 수 있는지도 확인한다(키트는 결과를 무시할 뿐 브라우저의 쿠키 변경은 막지 못한다). 보류 대상은 여러 탭 재발급을 조정하는 구체 방식과 서버·쿠키 격리 보장이다.
