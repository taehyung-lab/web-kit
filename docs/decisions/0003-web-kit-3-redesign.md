# 0003. web-kit 3.0: DT·레퍼런스에서 공용을 다시 뽑아 하나의 키트로 설계한다

- 상태: 채택 (2026-10-27, 사용자 합의)
- 관련 결정: [0002](0002-shared-foundation.md)를 전부 대체한다. [0001](0001-web-kit-1.0.md)의 수명 보장(세대 보호, 결과 출처, 저장 경합, E1–E3 보류)은 다시 검토할 출발점으로 남기고, 그 밖의 구조 선택은 이 기록이 대체한다.
- 근거 자료: DT v2(`dt-admin-web` v2), 레퍼런스(`zerosolution-reference-admin-web`), web-kit 2.0(`18a7e24`), starter(`519145e`)의 조사, 설계 보고서 `web-kit-redesign-2026-10-27/design-report.html`(작업 공간의 `reports/_archive-2026-10-27/`에 보관, 저장소 밖). 이 기록이 그 보고서와 2026-10-27의 이전 보고서들을 대체한다.

## 맥락

DT와 레퍼런스는 같은 바탕(React 19, TanStack Router·Query·Form·Table, Tailwind)에서 같은 일을 각자 만들고 있었다. 검색 조건을 주소에 담기, 기간·키워드 필터, 상태 5종을 가진 목록 표, 현재 페이지 선택과 일괄 작업, 첫 오류 칸 포커스·저장 확인·이탈 경고를 가진 폼, 진입 실패와 이후 실패를 구분하는 상세, 실패 12종과 토큰 재발급이 그렇다.

web-kit 2.0은 이 공통을 담으려 했지만 실제 화면 없이 먼저 만들어졌다. DT는 로직만 쓰고 화면 부품 9종을 다시 만들었고, 레퍼런스는 1.0.5에서 작은 도우미 7개만 썼다. 판단 기준이 문서마다 달라 UI 소유가 하루 안에 뒤집혔고, 30시간 동안 여섯 번 배포되며 내용이 다른 2.0.0 파일 두 개가 생겼다.

이번 결정은 기준을 하나로 고정하고, 실제 DT 화면이 키트로 완성될 때만 배포하게 한다.

## 결정

### 1. 방향

1. DT와 레퍼런스를 비교하고, 둘보다 나은 방식이 있으면 그것을 골라 공용을 새로 설계한다. 적용 대상은 DT v2다. 레퍼런스는 이번 단계에서 고치지 않는다.
2. DT 1.5는 사용자가 받아야 하는 결과(시나리오)와 실제 서버 동작의 근거다. 1.5의 코드·화면 배치는 옮기지 않는다. v2의 화면 내용과 구성은 1.5와 달라질 수 있다.
3. 2.0의 로직(실패·요청·세션 저장·쿼리·검색 상태·목록·저장 폼·단건)은 보장을 유지한 채 다시 검토한다. 화면 부품은 지우고 새로 만든다. 맞지 않는 공개 API는 3.0.0에서 교체하며 호환 래퍼로 두 소유자를 남기지 않는다.

### 2. 저장소와 배포

```
web-kit 저장소 (모노레포)
├─ packages/web-kit   하나의 패키지, 기능별 입구
└─ apps/starter       새 프로젝트의 틀이자 키트 소비 검사 앱
agent-workflow-kit    별도 저장소
dt-admin-web, 레퍼런스  각자 저장소, 배포된 버전만 사용
```

- 키트 기능을 바꾸는 PR에서 starter의 사용 코드도 함께 고친다. starter에 두 번째 공용 구현(상태 관리·오류 처리 등)을 만들지 않는다. starter에서 반복이 생기면 키트 책임이 빠진 신호로 본다.
- 검증은 배포할 tgz를 실제로 설치해서 한다. 모노레포 내부 소스 참조만으로 통과를 판정하지 않는다.
- 키트를 개발하는 작업 폴더에서만 DT가 키트 소스를 직접 가리킬 수 있다. DT 저장소에 올라가는 것은 항상 배포된 버전 번호다.
- 한 버전 번호에는 한 내용만 있다. 배포는 대표 화면이 아래 완료 기준을 통과한 단위로 한다.
- 발권(실시간 연결 SSE·STOMP, 발권 실행, 프린터)은 나중에 별도 패키지(`packages/ticketing`)로 만든다. 발권 전용 의존성(`@stomp/stompjs`, `sockjs-client`, 패치된 `event-source-polyfill`)을 한곳에 모으고, 공용 코드가 발권을 import하는 실수를 설치 단계에서 막기 위해서다. 지금은 폴더를 만들지 않는다. 세션은 발권을 import하지 않고, 발권이 세션 종료를 구독한다.
- auth 등 다른 패키지는 미리 만들지 않는다. 독립 소비자나 별도 의존성이 확인되면 `packages/` 아래에 추가한다.
- agent-workflow-kit는 웹과 무관한 작업 규칙이라 별도 저장소로 둔다. 프로젝트는 커밋 번호 대신 버전 태그로 고정하고, web-kit을 적용하는 PR에서 함께 올린다.

### 3. web-kit이 담는 것

| 기능 입구 | 키트가 맡는 것 | 프로젝트가 맡는 것 |
|---|---|---|
| failure / http / query | 실패 12종, 응답 봉투 해석, 동시 401의 재발급 합류와 최대 한 번 재전송, 쿼리 기본값 | 결과 코드표, 서버 주소, 운영 헤더, 재발급 endpoint·본문, 인증 거부 판정 |
| session | 인증 세대, 저장, 탭 동기화, 유휴 마감·경고·연장·종료, 종료 시 캐시 정리 순서 | 시간 정책, 서버 연장 함수, 로그인 경로, 만료 후 행동, 경고 디자인 |
| search / filter | 입력 중 초안과 확정 조건, 주소 복원, 검색 전 준비·검증, 초기화, 기간 계산, 키워드 칩 | 필드 의미, 기본값, 제공할 기간 preset, 서버 값 변환, API 시간대 계약 |
| list | 검색 전·로딩·빈 결과·실패·이전 결과 상태, 번호 페이지·총건수·정렬·페이지 크기, 현재 결과 기준 선택과 일괄 실행, 엑셀 다운로드 흐름 | 조회 함수, 컬럼, 선택 가능 조건, 일괄 명령과 확인 문구, 다운로드 범위 |
| form | 검증 실행, 중복 제출 잠금, 제출값 고정, 저장 중 편집 보존, 서버 필드 오류 부착(배열 하위 경로 포함), 오류 요약·구역 펼침·첫 오류 포커스, 이탈 경고, 저장 성공 확인→다음 이동, 모달 폼 제출 격리, 배열 행 정체성, 파일 보존 | 스키마, 요청 변환, 업무 사전검사, 저장 API, 업무상 필수 조건, 이동 목적지 |
| record | 레코드 격리, 로딩·없음·실패·갱신, 기본 항목 표시 | 항목 구성, 마스킹 정책, 이력 해석 |
| permission | 경로 진입 차단, 메뉴 숨김, 버튼 비활성의 틀(없으면 닫힘) | 권한 목록과 서버 자원·동작 대응 |

- 화면 부품은 기본 부품(버튼·입력·선택·체크박스·확인창·팝업·달력)과 묶음 부품(필터 영역, 기간·키워드 필드, 목록 표, 페이지 이동, 저장 폼, 상세 항목)을 shadcn + Base UI로 담는다. 화면 조립(어느 칸·필터·버튼이 있는지)은 프로젝트가 맡는다. 모양 차이는 디자인 토큰(CSS 변수)으로 다룬다.
- 부품은 상태에 연결된 작은 단위로 자유롭게 배치한다(예: `<List model={list}><List.Filter>…<List.Table/>…</List>`, `<Form.Root editor={editor}><Form.Section>…`). 필터 위치를 옮겨도 조회·정렬·선택 연결을 다시 쓰지 않는다. 한 화면 전체를 설정 객체로 그리는 방식은 쓰지 않는다.
- 입력칸 하나를 프로젝트 부품으로 바꿔 끼울 수 있고, 그래도 입력 상태와 검증은 키트가 맡는다. 필수 연결층(primitives adapter)은 두지 않는다.
- 모든 표를 주소 기반 목록으로 만들지 않는다. 상세 안의 하위 목록, 폼 배열, 선택 팝업은 표 표현만 공유하고 상태는 실제 수명에 맞춘다.

### 4. 구조 규칙

- 기능마다 입구가 따로 있고, import하지 않은 기능은 결과물에 들어가지 않는다.
- 의존은 한 방향이다. UI는 로직을 쓰고 로직은 UI를 import하지 않는다. 목록·폼은 세션 타이머·권한을 import하지 않는다.
- 모든 기능을 켜야 하는 필수 공통 설정을 만들지 않는다. 세션 타이머는 앱이 연결할 때만 시작하고, "만료 판단"과 "남은 시간 표시"를 따로 쓸 수 있다.
- 프로젝트 차이는 값으로만 받는다. "DT식 / 레퍼런스식" 같은 동작 분기 옵션은 만들지 않는다. 두 구현의 동작이 다르면 사용자가 손해 보지 않는 쪽 하나를 표준으로 정한다.

### 5. 목록의 표준 동작과 화면별 값

- 표준: 잘못된 값(선택지에 없는 값, 한쪽만 있거나 형식이 틀리거나 시작이 끝보다 늦은 날짜, 서버 선택지에 없는 ID)은 주소로 들어왔든 검색할 때 입력했든 그 칸만 기본값으로 되돌리고 나머지 조건으로 조회한다. 검색을 막고 문구를 띄우지 않는다. 필터를 제출하면 페이지만 1로 돌아가고 사용자가 바꾼 정렬·페이지 크기는 유지한다.
- 화면마다 정하는 값:
  - 조회 시작 조건: 들어오면 바로 조회 / 필수 조건이 채워지면 조회 / 검색을 눌러야 조회
  - 페이지 크기의 기본값과 선택지
  - 기본 정렬과 처음 누른 머리글의 정렬 방향

### 6. 세션 기준

DT의 [세션 결정](https://github.com/boosterlab-dev/dt-admin-web/blob/v2/docs/decisions/0001-session-warning-extend-requires-explicit-button.md)(2026-09-23)을 따른다.

- 경고 구간 밖의 사용자 조작은 활동 연장 간격마다 서버 연장을 부른다(유휴 30분 정책). 경고 구간 안에서는 연장 버튼만 연장한다(닫기·키 입력은 연장하지 않는다). 일반 API 응답·토큰 재발급은 마감을 늘리지 않는다(일반 응답은 서버 시계 보정에만 쓴다). 활동 연장 전면 폐기는 DT 결정 0001에서 기각됐다. 세부는 [0004](0004-session-idle-and-sign-out.md) §2.
- (2026-10-28 문장 정정: 이전 문장 "로그인과 명시적 연장만 유휴 마감을 바꾼다"가 활동 연장 금지로 읽혀 위처럼 고쳤다. 합의 내용은 바뀌지 않았다.)
- 재발급 요청 자체는 다시 재발급하지 않는다. 네트워크·timeout·5xx는 세션을 보존한다.
- 이전 로그인에서 시작한 요청·연장·저장 성공이 새 로그인에 반영되지 않는다.
- 만료 시 자격증명과 이전 사용자 캐시를 먼저 정리한 뒤 안내·이동한다. 서버 로그아웃 실패가 로컬 종료를 되돌리지 않는다.
- Web Locks가 없는 환경에서 모든 탭의 재발급이 한 번이라는 보장은 검증 전에는 약속하지 않는다.

## 순서

| 단계 | 산출물 |
|---|---|
| 1 | 이 결정 기록, 정리 대상 확인 |
| 2 | 저장소 구조(`packages/web-kit` + `apps/starter`), starter가 실제 tgz를 설치하는 검사 |
| 3 | 로그인·세션: 공용 수명 + DT 서버 adapter |
| 4 | 목록·필터·표·엑셀 다운로드·권한 틀(진입 차단·메뉴 숨김·버튼 비활성): 공연 목록 |
| 5 | 폼·상세: 운영자 등록·수정·상세. 2.0 확인창은 열린 직후 Tab 포커스가 밖에 남는 간헐 실패가 있다(starter `tests/e2e/browser.spec.ts` 「save confirmation traps focus」, 2단계 이전부터 3회 중 2회 실패). 새 확인창에서 해소한다 |
| 6 | 복잡한 폼 적합성: 공연 폼의 배열 오류 위치, 모달 제출 격리, 파일 보존 (공연 폼 전체 이관은 아님) |
| 7 | 실제 API 검증 후 web-kit 3.0.0 배포 |

그 뒤에 레퍼런스 이전, 발권 패키지, DT 나머지 화면 이관을 진행한다.

## 완료 기준

대표 화면 **로그인, 공연 목록, 운영자 폼**과 공연 폼 검사 사례가 아래를 모두 충족해야 키트 완료다. 결과는 충족·미충족·미확인으로 보고하며, 미충족·미확인이 남으면 완료가 아니고 배포하지 않는다.

1. 시나리오 달성: 1.5 시나리오에서 사용자가 하려던 일을 v2 화면에서 끝낼 수 있다(화면 구성은 달라도 된다). 아래 반례가 모두 실패로 잡힌다.
2. 서버 계약: 검색 API와 간단한 등록이 서버 명세대로 요청되어 dev 서버에서 성공하고, 등록 후 상세를 다시 조회한 값이 맞다. 시험 데이터는 `E2E-` 접두로 만들고 정리한다. mock 통과로 대신하지 않는다.
3. 설계 근거: 공용 부품·로직마다 DT·레퍼런스·다른 방식 비교와 고른 이유가 이 저장소 결정 기록에 남아 있다.
4. 중복 제거: DT 안의 자체 공용 부품이 지워졌고, 남긴 것은 이유가 기록되어 있다. 파일 이동이나 줄 수 감소만으로 판정하지 않는다.
5. 실제 설치: 배포할 tgz를 설치한 상태에서 1~4를 통과한다.
6. 레퍼런스 적합성: 레퍼런스의 "검색을 눌러야 조회"하는 회원 목록을 starter에서 키트의 값 설정만으로 재현한다.

1.5와 v2의 요청 비교(`dt-admin-web/scripts/scenarios/diff-golden.mjs`)는 참고용이다. 다른 요청은 화면 변경 때문인지 기록한다.

### 반드시 실패로 판정할 반례

- 검색 조건이 바뀌었는데 이전 행으로 일괄 변경이 실행된다.
- 키워드 입력 후 추가 버튼을 누르지 않고 검색하면 입력이 사라진다.
- 입력칸을 프로젝트 부품으로 바꾸거나 필터 UI를 숨기면 검증까지 사라진다.
- 검증 대기 중 두 번 저장되어 요청이 중복된다.
- 저장 중 편집한 값이 늦은 저장 성공으로 덮인다.
- 서버 저장은 성공했는데 이동 실패 후 다시 저장 요청이 나간다.
- 배열 이동 후 오류가 다른 행을 가리키거나 중첩 모달이 부모 폼도 제출한다.
- 만료 후 이전 사용자의 캐시가 남거나 이전 재발급 응답이 새 로그인을 덮는다.
- 일시적인 재발급 통신 실패만으로 로그아웃된다.
- 일반 API 응답이나 경고창 닫기가 유휴 시간을 다시 늘린다.
- 화면 배치·CSS만 바꿨는데 공통 상태 조립 코드를 다시 작성해야 한다.

## 검토한 대안

| 대안 | 판단 |
|---|---|
| 로직만 공유하고 화면은 각자 | 같은 부품을 프로젝트 수만큼 다시 만든다. DT의 현재 상태다. |
| 기본 부품만 키트에 | 반복되는 것은 묶음 부품이라 중복이 줄지 않는다. |
| 묶음 부품은 키트, 기본 부품은 프로젝트가 주입 | 프로젝트마다 연결층이 생긴다(레퍼런스 `primitives`). |
| 로직 키트와 화면 키트로 분리, 또는 기능마다 패키지 | 용량 차이는 없고 버전·호환표만 늘어난다. |
| 키트·DT·레퍼런스를 한 모노레포로 | 기술적으로 가장 깔끔하지만 회사 저장소 통합·배포·권한 재설계가 먼저 필요하다. 같은 팀이 맡는 프로젝트가 늘면 다시 검토한다. |
| 키트를 먼저 다 만들고 DT에 한꺼번에 적용 | 2.0의 실패 방식이다. 대표 화면 단위로 완성한다. |
