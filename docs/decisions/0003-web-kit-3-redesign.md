# 0003. 프로젝트에 독립적인 web-kit의 범위와 구조

- 상태: 2026-10-27 재설계 합의를 바탕으로, 2026-10-29 사용자 논의의 선택적 사용·페이지 일부 공용화 원칙을 반영했다. 구현·발행 완료를 뜻하지 않는다.
- 관계: 대체된 0002와 3.0 당시 작업 순서는 Git 이력에 남긴다. [0001](0001-web-kit-1.0.md)의 수명 결정 출처와 E1–E3 미확인은 보존한다. UI 배포 선택의 이유는 [0011](0011-web-kit-4-ui-distribution.md), 완료·발행 판정은 [유지보수](../maintaining.md#완료-기준)가 맡는다.
- 출처: 최초 비교는 DT v2, 레퍼런스, web-kit 2.0(`18a7e24`), starter(`519145e`)에서 출발했다. 이들은 요구와 검증 사례이며, 앞으로 모든 프로젝트가 따라야 할 제품 표준은 아니다.

## 맥락

실제 소비 화면 없이 공용 코드를 먼저 만들면, 소비처가 같은 상태·오류·저장 처리를 다시 만들게 된다. 반대로 특정 소비처 전체를 표준으로 삼으면 다른 제품의 요구가 프로젝트별 분기 옵션으로 쌓인다. 따라서 같은 책임과 관찰 가능한 동작을 공용화하고, 제품의 값·업무·화면 조립은 소비처에 둔다.

## 결정

### 1. 방향

1. 프로젝트는 필요한 공용 기능을 선택해 조립한다. web-kit은 채택한 기능의 공통 동작과 사용 기준을 제공하고, 프로젝트는 제품 요구·서버 계약·업무 처리·실제 화면을 소유한다.
2. 공용화는 사용하는 프로젝트 수나 화면의 닮은 정도만으로 정하지 않는다. 정상·실패·취소·늦은 응답 처리까지 같은 책임인지 비교한다. 두 프로젝트가 쓰더라도 특정 업무의 성공 판정이라면 프로젝트나 별도 업무 패키지가 맡는다.
3. 기존 시나리오는 보존할 제품 결과의 근거다. 키트를 쓰기 위해 승인되지 않은 제품 동작을 바꾸지 않는다. 현재 계약으로 표현할 수 없는 차이는 공용 보장의 결함·공통 기능 부족·제품 차이 중 무엇인지 먼저 구분한다.

### 2. 저장소와 배포

```
web-kit
├─ packages/web-kit       공통 동작·사용 스킬·적합성 검사
├─ packages/ui-registry   프로젝트로 복사할 UI·검사 연결 원본
└─ apps/starter           연결된 시작점이자 실제 산출물 소비 검사 앱
agent-workflow-kit        별도 저장소의 작업 판단·검증 방법
소비 프로젝트            고정한 버전의 기능을 선택해 제품에 연결
```

- 2026-10-29 추가 합의: 시작점은 이 저장소의 `apps/starter`다. 실행 가능한 예제 앱을 한 경로로 복사하고 기능별 입구·UI 선택 설치로 조립한다. 네 프로젝트 중 둘만 같은 기능을 써도 공용으로 둘 수 있으며, 값 차이·일부 기능 추가·업무 차이를 각각 입력·조합·프로젝트 연결로 처리한다. 기능 조합별 생성 옵션이나 별도 스타터 저장소는 만들지 않는다.
- starter는 모든 프로젝트의 표준 페이지가 아니다. 기본 연결과 조립 예를 제공하며 예시 필드·문구·권한은 제품 정책이 아니다. 공용 동작을 starter에서 다시 구현하지 않는다.
- starter는 포장한 패키지와 registry 복사본을 사용한다. 기능 변경 시 영향받는 사용 코드·검사를 함께 맞춘다. 예제가 쓰지 않는 기능은 별도 소비 검사 없이 검증됐다고 하지 않는다.
- 한 버전 번호에는 한 내용만 있다. 검사한 산출물과 발행할 산출물의 일치는 [유지보수](../maintaining.md#소비-검사와-발행)에서 판정한다. 개발 폴더의 직접 소스 참조는 발행 산출물의 소비 증거가 아니다.
- 발권(실시간 연결·프린터·발권 성공 판정)은 별도 업무 책임이다. 필요할 때 `packages/ticketing`으로 분리한다는 기존 결정을 유지하며, 아직 폴더를 만들지 않는다. 세션은 발권을 import하지 않고 발권이 세션 종료를 구독한다.
- 그 밖의 별도 패키지도 독립 소비자나 의존성·배포 요구가 확인될 때 판단한다. `/auth` 같은 기능별 입구를 추가하는 것과 패키지를 나누는 것은 다르다.
- agent-workflow-kit은 웹과 무관한 작업 방법을 제공한다. 프로젝트는 커밋 번호 대신 버전 태그로 고정하고, web-kit을 적용하는 PR에서 함께 올린다는 기존 결정을 유지한다. 태그가 아직 없는 후보 검증에서는 명시한 깨끗한 checkout과 해소된 커밋을 기록해 재현하며, 정식 태그 도입 완료로 표현하지 않는다. 이 문서 정리는 AWK 규칙이나 단계 호출 방식을 바꾸지 않는다.

### 3. web-kit이 담는 것

현재 기능·공개 입구는 [패키지 README](../../packages/web-kit/README.md#구조)와 `packages/web-kit/package.json`의 exports, 정확한 사용 보장은 같은 버전의 `packages/web-kit/skills/`가 정본이다. 이 기록에 동작 목록을 중복 관리하지 않는다.

공통 상태·진행은 패키지가 맡고, UI는 registry에서 복사하여 프로젝트가 소유한다([0011](0011-web-kit-4-ui-distribution.md)). 입력칸이나 배치를 바꿀 때도 패키지가 맡은 검증·잠금·상태 연결은 유지한다. 실제 채택 복사본에 공통 적합성 검사를 연결하고 제품의 요청·화면 결과는 프로젝트 검사로 확인한다.

#### 페이지 일부만 다른 경우

페이지 전체는 프로젝트가 조립한다. 같은 동작의 값 차이는 공개 입력으로 넘기고, 다른 업무 처리는 프로젝트 함수로 연결한다. 예를 들어 등록 폼의 검증·중복 제출 방지는 키트, 필드·요청 변환·승인 API·완료 목적지는 프로젝트가 맡는다. 파일 첨부가 있는 프로젝트만 필요한 첨부 UI를 조립한다.

- 모양만 바뀌면 UI 복사본을 수정한다. 같은 상태를 프로젝트에서 다시 관리하지 않는다.
- 업무가 다르면 해당 업무를 프로젝트에 둔다. 공통 저장 수명 전체를 복제하거나 키트 안에 프로젝트 이름별 분기를 넣지 않는다.
- 공개 입력·연결로 표현할 수 없으면 실제 요구와 적용 범위를 검토한다. 공통 보장 결함은 키트에서 고치고, 별도 제품 책임은 프로젝트에 둔다. 단지 서로 다르다는 이유로 모든 동작을 하나로 강제하지 않는다.
- 상세 안의 하위 목록·폼 배열·선택 팝업은 각자의 상태 수명에 맞춰 연결한다. 표 모양이 같다는 이유로 모두 URL 기반 목록으로 만들지 않는다.

### 4. 구조 규칙

- 기능마다 입구가 따로 있고, import하지 않은 기능은 결과물에 들어가지 않는다. 모든 기능을 켜야 하는 필수 공통 설정을 만들지 않는다.
- 의존은 한 방향이다. UI는 로직을 쓰고 로직은 프로젝트 UI를 import하지 않는다. 목록·폼은 세션 타이머·권한을 import하지 않는다.
- 같은 동작의 차이는 값으로 받는다. 서로 다른 동작은 공통으로 보장할 부분만 공유하고 나머지는 프로젝트가 선택·연결한다. `DT식/REF식` 분기는 만들지 않는다. 선택한 기능 안에서는 상태와 처리 순서의 소유자를 하나로 유지한다.
- 새 선택 기능과 기존 사용의 호환성은 [버전 기준](../maintaining.md#버전-기준)으로 판단한다. 이 원칙이 현재 공개 API에 없는 교체 지점을 이미 제공한다는 뜻은 아니다.

### 5. 목록의 표준 동작과 화면별 값

목록의 적용 조건과 보장은 [web-kit-list](../../packages/web-kit/skills/web-kit-list/SKILL.md)가 맡고, 설계 이유는 [0005](0005-list-filter-table-permission.md)와 [0010](0010-list-and-choice-agreements.md)에 남긴다. 기간 복구와 제품 검증의 적용 조건은 해당 스킬·공개 계약을 따른다. 조회 시작 조건·페이지 크기·정렬 기본값·필드 의미·요청 변환은 공개 계약 안에서 프로젝트가 정한다.

### 6. 세션 기준

세션·유휴 타이머의 적용 조건과 보장은 [web-kit-http](../../packages/web-kit/skills/web-kit-http/SKILL.md), 설계 이유는 [0004](0004-session-idle-and-sign-out.md)가 맡는다. 로그인 전 인증 단계는 [0012](0012-auth-challenge.md)의 별도 책임이다. 프로젝트는 시간 값·서버 연결·경로·문구를 정하며, 유휴 타이머를 채택하지 않은 제품에 그 정책을 강제하지 않는다. Web Locks가 없는 환경의 여러 탭 보장과 [0001](0001-web-kit-1.0.md)의 E1–E3는 확인 전까지 약속으로 승격하지 않는다.

## 완료 기준

기존 여섯 조건과 실패 반례는 [유지보수의 완료 기준](../maintaining.md#완료-기준)으로 옮겼다. 과거 판정의 `0003 완료 기준 1~6`은 그 번호에 대응한다. 이번 정리에서 3번의 필수 비교 대상을 특정 프로젝트 이름에서 실제 소비 요구·대안으로 바꾸었으며, 나머지 조건과 반례를 낮추지 않는다.

## 검토한 대안

- 페이지 전체를 공용 템플릿으로 고정하면 일부 업무 차이 때문에 공용 페이지에 분기가 쌓인다. 작은 기능을 프로젝트에서 조립한다.
- 로직만 제공하고 UI 연결을 매번 직접 만들면 포커스·이벤트 연결 결함을 반복한다. 기본 UI와 검사 연결을 registry로 제공하되 프로젝트가 표현을 소유한다.
- 기능마다 패키지를 먼저 나누면 실제 독립 배포 요구 없이 호환 조합만 늘어난다. 현재는 기능별 입구로 선택한다.
- 공용을 전부 만든 뒤 소비처에 한꺼번에 적용하면 실제 연결의 누락을 늦게 발견한다. 대표 흐름으로 확인하며 넓힌다.
