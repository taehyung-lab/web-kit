# 0001. web-kit 1.0 구조와 수명 계약

- 상태: 확정 (2026-10-23). E1–E3는 백엔드 확인 대기이며, 그에 걸린 부분만 보류한다. 수명 보장은 [0003](0003-web-kit-3-redesign.md)의 재검토 출발점으로 남고, 구조 선택은 0003이 대체한다.
- 근거: Codex·Claude의 독립 분석 → 상호 리뷰 → 통합 → 재대조를 거쳐 사용자가 확정한 내용이다(Orca run `run_ba2e78181cbd`).

## 기준

1. 누가 봐도 이해하기 쉬운 구조여야 한다. 화면 하나를 고칠 때 알아야 할 규칙이 실제로 줄어야 한다.
2. 덧붙이지 않고 근본을 해결한다. 같은 판단을 두 곳에서 하지 않고, 생기지 않는 경로에 가드를 달지 않으며, 옮긴 것은 원래 자리에서 지운다.
3. 현재 구현이 이렇다는 것은 근거가 아니다. 키트는 제품·업무 정책에 들어가지 않는다. 문서는 agent-workflow-kit 기준을 따른다.

**편입 규칙(U5):** 공통 보장을 완성하는 책임은 키트가 소유한다. 업무 의미 때문에 달라지는 흐름은 프로젝트가 조합한다. 특정 기능이 내부 변경을 요구한다는 사실만으로 키트에 포함하지 않는다.

## 구조

- core(입력만으로 결과를 정하는 순수 규칙, 루트로 공개, 라이브러리 import 없음)와 책임별 subpath로 나눈다. 세션처럼 실행·부수효과가 있는 코드는 라이브러리에 의존하지 않아도 core가 아니다. 다른 라이브러리가 필요해지면 binding subpath를 추가한다(Q1).
- 동작 코드와 module별 사용 문서는 키트가 갖는다. 시각 UI를 프로젝트에 두던 설계 B의 소유 범위는 [0002](0002-shared-foundation.md)에서 공통 기본 UI와 제품 표현으로 나눴다. 현재 구현 범위는 exports로 확인한다.
- module 사용 문서는 키트와 같은 버전으로 배포해 `docs/contracts.md`를 대체한다. 어떤 순서로 읽을지는 AGENTS.md 지도가 정한다(Q8).

## 결정

| 주제 | 결정 |
|---|---|
| 실패 (Q3·Q4) | 12종: network, timeout, cancelled, unauthorized, forbidden, validation, not-found, conflict, rate-limited, server-error, business, contract. status·code·requestId·fieldErrors를 담는다. 결과 코드 표는 `(status, code) → { kind?, messageKey, endsSession? }`이다. 실패는 가공하지 않고 그대로 전달한다. 키트가 보장하는 것은 두 가지다. 취소는 화면에 보이지 않고, 로그인 뒤의 401은 세션 쪽이 처리한다. |
| http·세션 (Q2, U1) | 요청 처리(요청 전송, 실패 변환, 허용된 재시도, 401 뒤 한 번 재전송)와 세션 수명(세대, 시작·종료 진입점, 여러 탭의 재발급 조정, 다른 탭 변경 감지)을 구분한다. 둘 다 키트가 소유하지만 interface는 따로 읽히고 고쳐진다. 세션 판정은 세션 수명 한 곳에서만 한다. 프로젝트는 토큰 저장 위치, idle, 종료 뒤 이동·안내를 맡는다. 재전송 뒤에는 추가 재발급을 하지 않는다. 세션 종료 여부는 확정된 인증 계약(결과 코드 표의 세션 종료 행, 재발급의 자격증명 거부·종료 행)으로만 판정하고 401 하나로 정하지 않는다. 인증 거절이 회전된 옛 토큰에 대한 것이면(요청이 쓴 토큰 ≠ 현재 토큰) 종료·재발급 없이 현재 토큰으로 다시 보낸다(DT 실측 4001, REF 기존 동작). 프로젝트 관찰(연결 상태·서버 시각)은 전송 시도마다 `observe` 하나로 받는다. 세대가 바뀐 뒤 도착한 결과는 키트의 토큰 저장·재전송·상태 반영에 들어가지 않는다. 이 보장은 클라이언트 반영 차단까지이며, 서버·쿠키의 세션 격리는 E3로 확인한다. |
| 세션 전환 (U2) | 세션이 바뀌면 이전 세션의 데이터 노출과 결과 반영을 막는다. 진행 중인 요청은 가능한 범위에서 중단하지만, 서버에서 이미 실행된 쓰기의 취소는 보장하지 않는다. |
| 재시도 (Q12) | 쓰기는 자동 재시도하지 않는다. 조회는 network·timeout·server-error일 때만 재시도하고 횟수는 프로젝트가 정한다. 쓰기 요청이 서버에 반영됐는지 확인할 수 없는 경우에만 "반영 여부 미확정"(`resultUnknown`)을 전달한다. 실패 종류만으로 반영 여부를 정하지 않으며, 요청 경로를 아는 http가 판정한다. 미확정이면 선언한 무효화로 다시 읽는다. |
| 검색 (Q5·Q11) | 키트가 검색 필드 선언(`defineSearch`) 전체를 소유한다(필드별 기본값 복구, 묶음, 정규 URL). 선택지에 의존하는 필드는 검증 함수를 선언하고, 그 검증에 실패하면 조회를 보류한다. |
| 목록 (Q6) | module 하나가 검색부터 선택까지 다룬다. |
| 폼 (Q7·Q9, U3) | 확인창 유무와 관계없이 저장 경로는 하나다. 확인창에 보여 준 S와 실제로 저장하는 S는 같다. 성공하면 저장 결과(폼 값으로 바꾼 값)가 기준선이 되고, 저장 결과가 없으면 S가 기준선이다. 저장 중 입력이 바뀌지 않았으면 저장 결과를 기준선과 현재 입력에 함께 반영한다. 바뀌었으면 현재 입력을 보존하고 기준선만 갱신한다(폼 전체 비교, 필드별 병합 없음). 원본이 다시 도착하면, 손대지 않은 폼은 교체하고, 고친 폼은 입력을 유지하며, 저장 중이면 교체하지 않는다. |
| 레코드 (Q10, U4) | 레코드 상태는 화면 안 한 곳에서 판정하고, loader는 미리 가져오기만 한다. 확인된 not-found와 현재 레코드 조회의 forbidden이면 이전 내용을 숨긴다. 다른 요청의 forbidden까지 숨김으로 확대하지 않는다. 일시적인 재조회 실패는 내용을 유지하고 갱신 실패 사실만 알린다. |
| 테스트 (Q13) | /testing의 3계층을 따른다. 재시도 뒤의 focus 규칙을 지키고, Field와 확인창부터 시작한다. |

## 보장의 출처

스킬의 보장 중 위 결정 표에 없는 것이 어디서 왔는지 적는다. 보장의 내용은 해당 스킬이 정본이다. 여기서는 이름과 위치만 가리킨다(내용을 다시 적으면 규칙이 바뀔 때 두 곳이 갈라진다). 새 보장을 스킬에 더할 때는 출처를 여기에 함께 적는다.

| 보장(내용은 스킬) | 출처 |
|---|---|
| 재발급 실패의 판정·늦은 재발급 결과·대기자 취소 (`web-kit-http` 재발급) | 통합안 http 계약(시작·진행·종료·늦은 결과 행) |
| 여러 탭 재발급의 직렬화 (`web-kit-http` 재발급) | 두 프로젝트의 기존 동작 유지. 구체 방식은 E3 확인 대기 |
| 확인 대기·저장 중 재제출, 늦은 결과 (`web-kit-form`) | 통합안 form 계약(진행·늦은 결과 행) |
| 선택지 확인의 key·늦은 응답·반복 복구 중단, 결과 출처, 일괄 작업 ID (`web-kit-list` 선택지 확인·결과 출처·선택) | 통합안 search·list 계약(시작·늦은 결과·결과 출처·일괄 작업 행) |
| 같은 식별 캐시의 시작 상태 (`web-kit-record`), 검색 변경·사라진 행의 선택 정리 (`web-kit-list` 선택) | 통합안 record 계약 시작 행, 0.4.0 `docs/contracts.md` list 5 |
| 일괄 작업 재실행, 같은 조건 재조회의 합류 (`web-kit-list` 확정·선택) | 독립 판정(2026-10-23) 지적: 구현에만 있거나 DT가 우회하던 동작을 보장으로 확정 |
| 선택지에 없는 URL 값의 복구 (`web-kit-list` 화면 선언·선택지 확인, 아래 구현 결정 「서버 선택지 확인」) | 사용자 결정(2026-10-26): "기간 뿐만 아니라 없는 타입이 들어온다거나 api를 통해 받은 옵션에서도 없으면 기본값으로" |

재발급 요청 전용 결과 코드 의미(E2의 "재발급 요청 각각")는 결과 코드 표가 아니라 프로젝트의 `reissue` adapter가 표현한다. adapter가 재발급 응답의 실패에 `endsSession`·`messageKey`를 실어 던지면 세션 수명이 그것으로 판정한다(키트의 재발급 seam). 일반 요청과 의미가 같으면(REF) 그대로 던진다.

## 백엔드 확인 (보류 범위)

- **E1:** 그 401 응답이 업무 실행 전에 발생하는가. 확인 전에는 쓰기를 자동으로 다시 보내지 않는다.
- **E2:** 일반 요청과 재발급 요청 각각에서 status·resultCode가 재발급 시도, 최종 인증 실패, 세션 종료 중 무엇을 뜻하는가. HTTP 200 봉투의 종결 코드도 포함한다. resultCode가 문자열(`'200'`·`'SUCCESS'`)로 오는 경우가 있는가(DT 방어 코드, 생성 계약은 숫자). 보류 대상은 결과 코드 표의 세션 종료 행이다.
- **E3:** 여러 탭이 동시에 재발급하면 어떻게 되는가. refresh 토큰을 회전하는지와 탭끼리 공유하는지, 이전 refresh 토큰을 다시 쓰면 어떻게 되는지, 회전 유예 시간, 먼저 발급한 access 토큰이 계속 유효한지를 확인한다. 로그아웃·계정 교체 뒤 이전 재발급 응답이 도착했을 때, 그 응답의 쿠키 변경이 새 세션에 영향을 줄 수 있는지도 확인한다(키트는 결과를 무시할 뿐 브라우저의 쿠키 변경은 막지 못한다). 보류 대상은 여러 탭 재발급을 조정하는 구체 방식과 서버·쿠키 격리 보장이다.

## 구현 결정

1.0을 확정하는 동안 구현 착수 전 분석, REF·DT·보일러플레이트 시험 적용, 독립 판정에서 바뀐 결정이다. 위 결정 표에 없는 현재 결정만 적는다. 어떤 실패에서 나왔는지는 git 이력(PR #3)에서 본다.

| 자리 | 결정 | 이유 |
|---|---|---|
| 폼 성공 | 저장 중 입력이 그대로면 저장 결과를 입력에도 반영하고, 바뀌었으면 기준선만 옮긴다 | 서버가 값을 정규화하면(공백 제거 등) 입력이 그대로인데 dirty로 남는다 |
| 폼 제출 | 제출 값은 복사하지 않는다. 제출 전 전체 검증은 blur 오류가 있어도 한다. `baseline`은 읽기 전용으로 낸다 | 복사는 File을 망가뜨린다(Form의 불변 갱신이 이미 고정한다) |
| 늦은 재발급 | 클라이언트 반영 차단까지만 보장한다. 쿠키 격리는 E3 | 응답의 Set-Cookie는 JS가 결과를 버려도 브라우저에 적용된다 |
| 재전송 뒤 401 | 추가 재발급은 없다. 세션 종료는 인증 계약(결과 코드 표)으로 판정한다 | 재시도를 끝내는 것과 세션을 끝내는 것은 다른 결정이다 |
| 쓰기 401 재전송 (E1) | 키트는 쓰기의 401을 재전송하지 않고 반영 여부 미확정으로 돌려준다. 인증이 업무 실행 전에 거절한다는 것을 확인해도 키트 상수를 바꾸지 않는다. 확인한 서버를 쓰는 프로젝트만 `createHttp` 입력으로 켠다(그때 입력을 추가한다) | 실행 전 거절 여부는 서버마다 다른 사실이다. 한 서버의 확인을 모든 소비자의 전제로 만들지 않는다 |
| 반영 여부 미확정 | 반영 여부를 확인할 수 없는 경우만 `resultUnknown`이다. http가 판정한다 | 쓰기의 모든 network·timeout을 미확정으로 보면 하지 않은 업무까지 확인 대상이 된다 |
| 회전된 옛 토큰 | 그 토큰의 인증 거절은 현재 토큰으로 재전송한다. 새 근거가 있을 때만 반복한다 | 여러 탭·재발급 직후에 옛 토큰으로 나간 요청이 생긴다 |
| 재발급 실패 | 재발급 응답도 결과 코드 표로 판정하고, 종료 행이면 그 실패가 세션 종료 사유다. 재발급 전용 의미는 프로젝트 `reissue` adapter가 `endsSession`·`messageKey`로 표현한다 | 결과 코드 의미는 서버마다 다르다 |
| 전송 관찰 | http의 입력 `observe` 하나로 연결 상태·응답 헤더를 프로젝트가 본다 | 편입 규칙: 프로젝트가 조합할 수 없을 때만 interface를 바꾼다 |
| 실패 해석 | 422 → validation. 필드 오류는 `data` 배열과 `data.invalidMessages`만 읽는다. 실패 판별은 전역 Symbol 표시로 한다 | 한 앱에 키트가 두 벌 로드되면(monorepo) `instanceof`가 실패한다 |
| 실패 입력 | `RequestFailure`가 `messageKey`·`endsSession`을 직접 받는다. 세션 종료는 출처 `by`를 싣고, 쓰기 실패도 출처와 함께 `notify`한다 | 프로젝트가 우회 코드를 만들지 않게 한다 |
| 레코드 | `useRecord`는 레코드 식별을 따로 받고, 준비된 식별 하나로 이전 내용을 유지할지 정한다. `missing.wasReady`는 사실만 주고 표시 위치는 프로젝트가 정한다 | 언어 전환에도 폼을 지키고, 식별이 바뀐 뒤 이전 레코드가 ready로 보이지 않게 한다 |
| 검색 URL | `validateSearch`는 정규 URL 표현을 낸다. `beforeLoad`는 진입 주소를 그 표현으로 replace한다. 필드 `encode`, 묶음 `{ fields, valid? }`, 보기 key는 `view`로 선언한다 | Router는 진입 주소를 고치지 않는다. URL key는 제품 계약이다 |
| 서버 선택지 확인 | `check: { parents?, options, allowed }`. 확인은 그 선택지 query의 observer다. 없는 값은 버리고, 배열은 선택지에 있는 항목만 남긴다 | 필터 UI와 같은 query 상태를 따라야 취소·재시도가 맞는다. 배열 처리는 고정 목록의 항목 복구와 같은 규칙이다 |
| 목록 | 초안 변환은 `draft: { from, to }`이고, 초안 수명은 필터 부분 기준이다. 화면 `enabled`는 함께 지킨다(`not-ready`). 응답 타입은 제네릭으로 받아 `page`로 낸다. `refresh()`는 진행 중 요청에 합류한다 | 화면이 같은 조회를 두 번 읽거나 조건을 덮어쓰지 않게 한다 |
| 저장 결과 | `onSaved(result)`가 저장 함수의 결과를 받는다. loader는 기다리지 않고 실패를 삼키는 `queryClient.query(options)`를 쓴다 | 등록 뒤 새 id로 이동하는 데 우회가 필요 없게 한다. `prefetchQuery`는 설치 버전에서 deprecated다 |
| 소스 배포 | 키트 tsconfig에 `noUnusedLocals`·`noUnusedParameters`를 둔다 | 소비 앱이 키트 소스를 컴파일한다 |
| 반영 안 함 | 문자열 resultCode(생성 계약은 숫자, E2에서 확인), resultMessage 문구 조회(결과 코드 표 행으로 대신함), 요청별 응답 헤더(axios 표준 기능으로 조합됨), 묶음 복구 값 지정(기본값 하나 유지), 빈 이전 페이지 구분 | 다시 제안하지 않도록 남긴다 |
